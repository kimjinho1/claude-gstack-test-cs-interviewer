# 04-07 락 (공유락, 배타락, 데드락)

## 개념

**락(Lock)**: 동시 트랜잭션 간의 데이터 충돌을 방지하는 메커니즘.

```
공유락 (Shared Lock, S): 읽기용. 여러 트랜잭션이 동시 보유 가능
배타락 (Exclusive Lock, X): 쓰기용. 하나만 보유, 다른 락과 충돌

호환성:
        보유 중인 락
  요청  |  S  |  X
  S    | OK  | 대기
  X    | 대기 | 대기
```

---

## 동작 원리

### 락 종류

```
행 락 (Row Lock, InnoDB):
  특정 행만 잠금 → 높은 동시성
  SELECT ... FOR UPDATE: 배타락
  SELECT ... FOR SHARE: 공유락

테이블 락 (Table Lock, MyISAM):
  테이블 전체 잠금 → 낮은 동시성
  대량 배치 작업에 효율적

페이지 락 (Page Lock):
  행 락과 테이블 락의 중간

의도 락 (Intention Lock):
  계층적 락 지원 — 테이블에 IS/IX 표시
  IS (Intention Shared): 자식(행)에 S락 예정
  IX (Intention Exclusive): 자식(행)에 X락 예정
```

### Deadlock

```
T1: 행A 락 → 행B 락 시도 (행B는 T2가 보유)
T2: 행B 락 → 행A 락 시도 (행A는 T1이 보유)
→ 서로 기다림 → 무한 대기 = 데드락

탐지: Wait-for Graph 사이클 검사
     → 사이클 발견 시 한 트랜잭션 강제 종료(희생자 선택)

예방 전략:
  1. 항상 같은 순서로 락 획득 (행A → 행B → 행C 순서 고정)
  2. 타임아웃 설정 (innodb_lock_wait_timeout = 50초 기본)
  3. 트랜잭션을 짧게 유지
  4. SELECT FOR UPDATE 최소화
```

### 낙관적 락 vs 비관적 락

```
비관적 락 (Pessimistic Lock):
  - 수정할 것이라 가정 → 미리 락 획득
  - SELECT FOR UPDATE → 조회와 동시에 락
  - 충돌 많은 환경: 데이터 정합성 보장
  - 단점: 락 경합으로 성능 저하

낙관적 락 (Optimistic Lock):
  - 충돌이 적다고 가정 → 락 없이 읽기
  - 수정 시 버전/타임스탬프 확인
  - UPDATE ... WHERE id=? AND version=?
    → 영향 행 수 = 0이면 충돌 → 재시도
  - 충돌 적은 환경: 높은 동시성
  - 단점: 충돌 많으면 재시도 오버헤드
```

## 예시 코드 (Python)

```python
import sqlite3
import threading
import time
import random


# ── 락 경합 시연 ─────────────────────────────────────

def lock_contention_demo():
    conn = sqlite3.connect(":memory:", check_same_thread=False)
    conn.execute("""
        CREATE TABLE accounts (
            id      INTEGER PRIMARY KEY,
            name    TEXT,
            balance INTEGER
        )
    """)
    conn.executemany("INSERT INTO accounts VALUES (?,?,?)", [
        (1, "A계좌", 10000), (2, "B계좌", 10000)
    ])
    conn.commit()

    lock = threading.Lock()
    results = []

    def transfer(from_id, to_id, amount, txn_name):
        with lock:
            try:
                conn.execute("BEGIN IMMEDIATE")
                # 잔액 확인
                bal = conn.execute(
                    "SELECT balance FROM accounts WHERE id=?", (from_id,)
                ).fetchone()[0]
                if bal < amount:
                    conn.execute("ROLLBACK")
                    results.append(f"{txn_name}: 잔액 부족 ({bal} < {amount})")
                    return
                time.sleep(0.01)   # 의도적 지연
                conn.execute(
                    "UPDATE accounts SET balance=balance-? WHERE id=?",
                    (amount, from_id)
                )
                conn.execute(
                    "UPDATE accounts SET balance=balance+? WHERE id=?",
                    (amount, to_id)
                )
                conn.execute("COMMIT")
                results.append(f"{txn_name}: 이체 성공 ({amount}원)")
            except Exception as e:
                conn.execute("ROLLBACK")
                results.append(f"{txn_name}: 실패 - {e}")

    threads = [
        threading.Thread(target=transfer, args=(1, 2, 3000, "T1: A→B")),
        threading.Thread(target=transfer, args=(2, 1, 2000, "T2: B→A")),
        threading.Thread(target=transfer, args=(1, 2, 8000, "T3: A→B 대량")),
    ]
    [t.start() for t in threads]
    [t.join() for t in threads]

    print("[락 경합 결과]")
    for r in results:
        print(f"  {r}")

    rows = conn.execute(
        "SELECT name, balance FROM accounts ORDER BY id"
    ).fetchall()
    total = sum(r[1] for r in rows)
    print(f"  최종 잔액: {dict(rows)}")
    print(f"  총합: {total} (초기: 20000) — {'일치 ✓' if total==20000 else '불일치 ✗'}")
    conn.close()


# ── 낙관적 락 (버전 컬럼) ────────────────────────────

def optimistic_lock_demo():
    conn = sqlite3.connect(":memory:", check_same_thread=False)
    conn.execute("""
        CREATE TABLE devices (
            id       INTEGER PRIMARY KEY,
            hostname TEXT,
            config   TEXT,
            version  INTEGER DEFAULT 0   -- 낙관적 락용 버전
        )
    """)
    conn.execute("INSERT INTO devices VALUES (1, 'sw-core-01', 'vlan 10', 0)")
    conn.commit()

    success_count = [0]
    retry_count   = [0]
    lock = threading.Lock()

    def update_config(new_config: str, worker_id: int):
        """낙관적 락: 버전 확인 후 업데이트, 충돌 시 재시도"""
        max_retries = 5
        for attempt in range(max_retries):
            with lock:
                row = conn.execute(
                    "SELECT config, version FROM devices WHERE id=1"
                ).fetchone()
                if not row:
                    return

                current_config, version = row
                time.sleep(random.uniform(0, 0.01))  # 경쟁 유도

                # 버전 조건: 내가 읽은 버전 그대로이면 업데이트
                affected = conn.execute("""
                    UPDATE devices
                    SET config=?, version=version+1
                    WHERE id=1 AND version=?
                """, (new_config, version)).rowcount
                conn.commit()

            if affected > 0:
                success_count[0] += 1
                return  # 성공
            else:
                retry_count[0] += 1  # 충돌 → 재시도
                time.sleep(0.001 * (2 ** attempt))  # Exponential backoff

    configs = [f"config_v{i}" for i in range(10)]
    threads = [
        threading.Thread(
            target=update_config,
            args=(cfg, i)
        )
        for i, cfg in enumerate(configs)
    ]
    [t.start() for t in threads]
    [t.join() for t in threads]

    final = conn.execute("SELECT config, version FROM devices WHERE id=1").fetchone()
    print(f"\n[낙관적 락]")
    print(f"  성공: {success_count[0]}, 재시도: {retry_count[0]}")
    print(f"  최종 config={final[0]}, version={final[1]}")
    conn.close()


# ── 데드락 시나리오 및 방지 ──────────────────────────

def deadlock_prevention_demo():
    """
    데드락 방지: 항상 같은 순서(id 오름차순)로 락 획득
    """
    conn = sqlite3.connect(":memory:", check_same_thread=False)
    conn.execute("CREATE TABLE rows (id INT PRIMARY KEY, val INT)")
    conn.executemany("INSERT INTO rows VALUES (?,?)", [(1,100),(2,200)])
    conn.commit()

    py_lock_1 = threading.Lock()
    py_lock_2 = threading.Lock()
    results = []

    def safe_transfer(from_row, to_row, amount, name):
        """락 순서 고정 (id 오름차순) → 데드락 방지"""
        first, second = (py_lock_1, py_lock_2) if from_row < to_row \
                        else (py_lock_2, py_lock_1)
        with first:
            time.sleep(0.005)
            with second:
                conn.execute("UPDATE rows SET val=val-? WHERE id=?", (amount, from_row))
                conn.execute("UPDATE rows SET val=val+? WHERE id=?", (amount, to_row))
                conn.commit()
                results.append(f"{name}: 성공")

    threads = [
        threading.Thread(target=safe_transfer, args=(1, 2, 50, "T1")),
        threading.Thread(target=safe_transfer, args=(2, 1, 30, "T2")),
    ]
    [t.start() for t in threads]
    [t.join() for t in threads]

    print(f"\n[데드락 방지 (락 순서 고정)]")
    for r in results:
        print(f"  {r}")
    rows = conn.execute("SELECT id, val FROM rows ORDER BY id").fetchall()
    total = sum(r[1] for r in rows)
    print(f"  최종: {dict(rows)}, 총합={total} (초기 300) {'✓' if total==300 else '✗'}")
    conn.close()


# ── 실행 ─────────────────────────────────────────────

print("=== 락 경합 ===")
lock_contention_demo()

print("\n=== 낙관적 락 ===")
optimistic_lock_demo()

deadlock_prevention_demo()
```

## 면접 예상 질문

- Q: 공유락과 배타락의 차이는?
  A: 공유락(S)은 읽기용 — 여러 트랜잭션이 동시에 보유 가능, 서로 간섭 없음. 배타락(X)은 쓰기용 — 하나만 보유, S락과도 충돌. SELECT는 MVCC로 락 없이 읽음. SELECT FOR UPDATE는 배타락, SELECT FOR SHARE는 공유락 획득.

- Q: 데드락이란? 어떻게 방지하나?
  A: 두 트랜잭션이 서로 상대방의 락을 기다려 무한 대기하는 상태. InnoDB는 Wait-for Graph로 사이클 감지 → 비용이 낮은 트랜잭션을 희생자로 선택해 롤백. 방지: ① 락 획득 순서 고정 (항상 같은 순서로), ② 트랜잭션을 짧게, ③ 필요한 락 범위 최소화, ④ innodb_lock_wait_timeout 설정.

- Q: 낙관적 락과 비관적 락의 차이는?
  A: 비관적 락 — 충돌이 많다고 가정, 미리 락 획득(SELECT FOR UPDATE). 데이터 정합성 강하지만 동시성 저하. 낙관적 락 — 충돌이 드물다고 가정, 버전/타임스탬프로 충돌 감지. UPDATE WHERE version=? → 영향 행 수 확인. 충돌 적은 읽기 위주 환경에서 높은 동시성. 충돌 많으면 재시도 오버헤드 발생.
