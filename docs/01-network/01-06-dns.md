# 01-06 DNS (Domain Name System)

## 개념

도메인 이름(`google.com`)을 IP 주소(`142.250.196.46`)로 변환하는 **분산 계층 시스템**.
사람이 기억하기 쉬운 이름 ↔ 기계가 사용하는 IP 주소를 매핑.

- 프로토콜: UDP 53번 포트 (응답이 512byte 초과 시 TCP로 전환)
- 전 세계 분산 구조 → 단일 장애점 없음

---

## 동작 원리

### DNS 계층 구조

```
.  (Root)                ← 전 세계 13개 Root DNS 서버
├── com  (TLD)           ← .com 담당 TLD DNS
│   ├── google.com       ← 구글이 직접 관리하는 Authoritative DNS
│   └── naver.com
├── net
└── kr
    └── co.kr
```

### PC가 www.google.com에 접속할 때 전체 흐름

브라우저 주소창에 `www.google.com` 입력 → Enter 누를 때 실제로 일어나는 일 순서대로:

```
① 브라우저 캐시 확인
   "www.google.com 최근에 접속했나?" → 있으면 바로 사용

② OS DNS 캐시 확인
   브라우저 캐시 없으면 OS 캐시 확인
   Windows: ipconfig /displaydns
   Linux:   systemd-resolved 캐시

③ hosts 파일 확인
   /etc/hosts (Linux/Mac) 또는 C:\Windows\System32\drivers\etc\hosts
   "192.168.99.1  sw-core-01.local" 같은 정적 매핑 확인
   → 있으면 DNS 쿼리 없이 바로 이 IP 사용

④ Local DNS 서버에 쿼리 (여기서부터 실제 DNS)
   PC → Local DNS(ISP/회사 DNS): "www.google.com A 레코드 줘"
   Local DNS에 캐시 있으면 바로 응답 → ⑨로

⑤ Local DNS → Root DNS
   Local DNS: "www.google.com 모름, root한테 물어봄"
   Root DNS: "com은 TLD DNS a.gtld-servers.net가 담당"

⑥ Local DNS → TLD DNS (.com)
   TLD DNS: "google.com은 ns1.google.com이 담당 (Auth DNS)"

⑦ Local DNS → Auth DNS (ns1.google.com)
   Auth DNS: "www.google.com A 레코드 = 142.250.196.46, TTL=300"

⑧ Local DNS → PC 응답
   캐시에 저장 (TTL=300초 동안)
   PC에 142.250.196.46 반환

⑨ TCP 연결 (3-way handshake)
   PC → 142.250.196.46:443 SYN

⑩ TLS handshake
   인증서 검증, Session Key 협상

⑪ HTTP 요청
   GET / HTTP/2
   Host: www.google.com

⑫ 화면 렌더링
```

```
전체 타임라인:
[DNS 조회: 수ms~수십ms] → [TCP 연결: 1RTT] → [TLS: 1RTT] → [HTTP: 1RTT]

캐시 HIT 시: DNS 조회 단계 스킵 → 훨씬 빠름
HTTP/3(QUIC): TCP+TLS 합쳐서 1RTT → 더 빠름
```

### 조회 흐름 다이어그램

```
PC              Local DNS        Root DNS    TLD(.com)   Auth(google)
│                │                 │           │              │
│─"www.google.com?"──────────────▶│           │              │
│                │ (캐시 없음)      │           │              │
│                │─"com 담당 누구?"─▶│           │              │
│                │◀─"TLD 주소 알려줌"─│           │              │
│                │─────────────"google 담당?"──▶│              │
│                │◀───────────"Auth DNS 주소"───│              │
│                │───────────────────────────────────"www?"───▶│
│                │◀──────────────────────────────────"142.x.x.x"│
│◀─"142.x.x.x"──│                 │           │              │
│  TTL 캐시 저장  │                 │           │              │
│                │                 │           │              │
│─ TCP SYN ─────────────────────────────────────────────────▶│ (142.x.x.x:443)
│◀─ SYN-ACK ─────────────────────────────────────────────────│
│─ ACK + TLS ClientHello ───────────────────────────────────▶│
│◀─ TLS 협상 완료 ────────────────────────────────────────────│
│─ GET / HTTP/2 ─────────────────────────────────────────────▶│
│◀─ 200 OK ───────────────────────────────────────────────────│
```

**Recursive vs Iterative**
- **Recursive**: Local DNS가 대신 Root→TLD→Auth 다 돌아다니며 찾아줌. PC는 한 번만 요청.
- **Iterative**: 각 DNS가 "다음에 물어봐" 주소만 알려줌. 실제 요청자가 단계별로 직접 물어봄.

실제로 PC↔Local DNS는 Recursive, Local DNS↔나머지는 Iterative.

### 캐시와 TTL

DNS 응답에는 **TTL(Time To Live)** 포함. TTL만큼 캐시에 저장.

```
조회 순서:
1. PC 로컬 캐시 (hosts 파일 포함)
2. Local DNS 캐시
3. 없으면 계층 조회 시작
```

- TTL 짧음(예: 60초): IP 변경 빠르게 반영, DNS 쿼리 증가
- TTL 길음(예: 86400초=1일): DNS 부하 낮음, IP 변경 반영 느림
- 스위치/AP 관리 도메인 IP 변경 시 → TTL 만료 전까진 구 IP로 접속

## 주요 DNS 레코드 타입

| 레코드 | 역할 | 예시 |
|--------|------|------|
| A | 도메인 → IPv4 주소 | `api.switch.local → 192.168.99.10` |
| AAAA | 도메인 → IPv6 주소 | `google.com → 2607:f8b0::` |
| CNAME | 도메인 → 도메인 (별칭) | `www.google.com → google.com` |
| MX | 메일 서버 지정 | `gmail.com → mail.google.com` |
| NS | 네임서버 지정 | `google.com → ns1.google.com` |
| PTR | IP → 도메인 (역방향 조회) | `192.168.99.10 → sw-core-01.local` |
| TXT | 텍스트 정보 | SPF, DKIM (메일 인증), 도메인 소유 확인 |
| SRV | 서비스 위치 | `_http._tcp.example.com → 포트/호스트` |

**스위치/AP 관리 관점**
- A 레코드: `sw-core-01.mgmt.local → 192.168.99.1` (이름으로 장비 접속)
- PTR 레코드: Syslog/SNMP에서 IP → 장비명 역방향 변환
- 내부 DNS 서버 없으면 `/etc/hosts`에 수동 등록

## 예시 코드 (Python)

```python
import socket
import struct
import random


def parse_dns_response(data: bytes) -> list[str]:
    """DNS 응답에서 IP 주소 추출 (간단 버전)"""
    ips = []
    # 헤더 12byte 스킵, ANCOUNT(응답 수) 추출
    ancount = struct.unpack(">H", data[6:8])[0]
    offset = 12

    # Question 섹션 스킵
    while data[offset] != 0:
        if data[offset] >= 192:  # 압축 포인터
            offset += 2
            break
        offset += data[offset] + 1
    else:
        offset += 5  # null + QTYPE(2) + QCLASS(2)

    # Answer 섹션 파싱
    for _ in range(ancount):
        if data[offset] >= 192:  # 압축 포인터
            offset += 2
        else:
            while data[offset] != 0:
                offset += data[offset] + 1
            offset += 1

        rtype = struct.unpack(">H", data[offset:offset+2])[0]
        rdlength = struct.unpack(">H", data[offset+8:offset+10])[0]
        offset += 10

        if rtype == 1 and rdlength == 4:  # A 레코드
            ip = ".".join(str(b) for b in data[offset:offset+4])
            ips.append(ip)
        offset += rdlength

    return ips


def dns_query(domain: str, dns_server: str = "8.8.8.8") -> list[str]:
    """UDP DNS 쿼리 전송 및 응답 파싱"""
    # DNS 쿼리 패킷 생성
    transaction_id = random.randint(0, 65535)
    flags = 0x0100          # Recursion Desired
    qdcount = 1             # 질문 1개

    header = struct.pack(">HHHHHH", transaction_id, flags, qdcount, 0, 0, 0)

    # QNAME 인코딩: www.google.com → \x03www\x06google\x03com\x00
    qname = b""
    for part in domain.split("."):
        qname += bytes([len(part)]) + part.encode()
    qname += b"\x00"

    qtype = struct.pack(">H", 1)   # A 레코드
    qclass = struct.pack(">H", 1)  # IN (Internet)

    query = header + qname + qtype + qclass

    # UDP로 전송
    with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as s:
        s.settimeout(3)
        s.sendto(query, (dns_server, 53))
        response, _ = s.recvfrom(512)

    return parse_dns_response(response)


# Python 내장 DNS 조회 (실무에서는 이걸 씀)
def simple_dns_lookup(domain: str) -> list[str]:
    """socket.getaddrinfo로 DNS 조회"""
    results = socket.getaddrinfo(domain, None, socket.AF_INET)
    return list(set(r[4][0] for r in results))


# DNS 캐시 시뮬레이션
import time
from dataclasses import dataclass, field


@dataclass
class DnsRecord:
    domain: str
    ips: list[str]
    ttl: int
    cached_at: float = field(default_factory=time.time)

    def is_expired(self) -> bool:
        return time.time() - self.cached_at > self.ttl


class DnsCache:
    def __init__(self):
        self._cache: dict[str, DnsRecord] = {}

    def get(self, domain: str) -> list[str] | None:
        record = self._cache.get(domain)
        if record and not record.is_expired():
            remaining = record.ttl - (time.time() - record.cached_at)
            print(f"[DNS Cache] HIT: {domain} → {record.ips} (TTL 잔여 {remaining:.0f}s)")
            return record.ips
        if record:
            print(f"[DNS Cache] EXPIRED: {domain}")
            del self._cache[domain]
        return None

    def set(self, domain: str, ips: list[str], ttl: int):
        self._cache[domain] = DnsRecord(domain=domain, ips=ips, ttl=ttl)
        print(f"[DNS Cache] STORE: {domain} → {ips} (TTL={ttl}s)")


# 사용 예시
cache = DnsCache()
cache.set("sw-core-01.mgmt.local", ["192.168.99.1"], ttl=300)
cache.get("sw-core-01.mgmt.local")   # HIT
cache.get("sw-edge-01.mgmt.local")   # None (없음)

# 실제 DNS 조회
print("\n[실제 DNS 조회]")
ips = simple_dns_lookup("google.com")
print(f"google.com → {ips}")
```

## 부록: DNS 공격 상세

### 1. DNS Cache Poisoning (캐시 포이즈닝)

**원리**: DNS는 UDP 기반이라 응답 패킷을 인증하지 않음. 공격자가 정상 응답보다 빨리 위조 응답을 보내면 Local DNS 캐시에 허위 레코드가 저장됨.

```
정상 흐름:
Local DNS ──"www.bank.com?"──▶ Auth DNS
Local DNS ◀──"203.x.x.x"────── Auth DNS (진짜 IP)

공격 흐름:
Local DNS ──"www.bank.com?"──▶ Auth DNS
공격자    ◀─ 요청 패킷 스니핑
공격자    ──"www.bank.com = 1.2.3.4"──▶ Local DNS (위조 응답, Auth보다 빨리)
Local DNS: 먼저 도착한 응답 저장 → TTL 동안 오염

결과:
모든 사용자: www.bank.com → 1.2.3.4 (공격자 서버) → 피싱 페이지
```

**Kaminsky 공격 (2008년)**

Transaction ID가 16bit(0~65535)라 랜덤 포트 없던 시절 1초에 예측 가능.
수천 개 위조 응답을 쏟아부어 캐시 오염. 인터넷 전체 위협.
→ 이후 소스 포트 랜덤화(16bit 추가) 도입 → 예측 공간 2^32로 증가.

**대응**:
- **DNSSEC**: Auth DNS가 응답에 디지털 서명 → 위조 불가
- 소스 포트 랜덤화: Transaction ID(16bit) + 랜덤 포트(16bit) = 2^32 예측 공간
- DoH/DoT: DNS 쿼리 자체를 암호화 → 스니핑 불가

### 2. DNS Spoofing

캐시 포이즈닝의 상위 개념. Local DNS 오염 외에도:
- 라우터/AP를 장악해 DNS 서버 주소 자체를 공격자 서버로 변경
- DHCP 응답에 악성 DNS 서버 주입

```
악성 AP 시나리오:
사용자 AP 접속 → DHCP로 DNS=192.168.1.99(공격자) 할당
모든 DNS 쿼리 → 공격자 DNS 서버 → 원하는 도메인으로 유도
```

### 3. DNS Amplification (증폭 DDoS)

DNS 응답이 요청보다 훨씬 크다는 점을 이용한 DDoS 증폭 공격.

```
공격 원리:
공격자: 출발지 IP를 피해자 IP로 위조
        ANY 레코드 요청 (응답 크기 최대화)
        → 오픈 DNS 리졸버들에게 대량 전송

오픈 DNS 리졸버: 요청(60byte) → 응답(3000byte) → 피해자에게 전송
증폭 비율: 50배

피해자: 수천 개 DNS 서버의 응답이 동시에 쏟아짐 → 대역폭 고갈
```

**대응**:
- 오픈 리졸버 차단: 내부 IP만 쿼리 허용
- Response Rate Limiting (RRL): 동일 소스 응답 속도 제한
- BCP38: ISP 레벨 출발지 IP 위조 패킷 차단

### 4. DNS Hijacking

DNS 쿼리 자체를 가로채 응답 조작.

```
유형별:
① 로컬 호스트 hijacking: 악성코드가 hosts 파일 수정
② 라우터 hijacking: 라우터 DNS 설정 변경 (관리 취약점)
③ ISP 레벨 hijacking: ISP가 의도적으로 NXDOMAIN 대신 광고 페이지로
④ 국가 레벨 hijacking: 특정 도메인을 차단/리디렉션
```

### 5. DNS Tunneling

DNS 쿼리/응답을 데이터 채널로 악용. 방화벽이 HTTP를 막아도 DNS(53)는 열려있는 경우 많음.

```
공격자 C2 서버 도메인: c2.evil.com

명령 전달:
  DNS 쿼리: "aGVsbG8=.c2.evil.com" (Base64 인코딩된 명령)
  DNS 응답: TXT 레코드에 Base64 인코딩된 결과 반환

외부로 데이터 유출:
  DNS 쿼리 서브도메인에 데이터 조각을 숨겨서 전송
```

**대응**: DNS 쿼리 길이/빈도 이상 감지, DNS 트래픽 분석(DGA 탐지).

### DNS 공격 대응 정리

| 공격 | 핵심 대응 |
|------|---------|
| Cache Poisoning | DNSSEC, 소스 포트 랜덤화 |
| DNS Spoofing | DNSSEC, DoH/DoT |
| Amplification DDoS | 오픈 리졸버 차단, RRL |
| DNS Hijacking | DNSSEC, 라우터 강화, DoH |
| DNS Tunneling | DNS 이상 트래픽 모니터링 |

**DNSSEC vs DoH vs DoT**

```
DNSSEC : DNS 응답의 무결성 검증 (위조 방지). 암호화는 아님.
DoT    : DNS over TLS. DNS 쿼리 자체를 TLS 암호화. 포트 853.
DoH    : DNS over HTTPS. DNS를 HTTPS로 전송. 포트 443.
         방화벽/ISP가 DNS 트래픽 구분 불가 → 프라이버시 강화.
```

## 면접 예상 질문

- Q: 브라우저에서 URL 입력 후 화면이 뜨기까지 과정을 설명하라.
  A: ① 브라우저/OS/hosts 캐시 확인 → ② Local DNS에 도메인 쿼리 → ③ Local DNS가 Root→TLD→Auth 순으로 Iterative 조회 → ④ IP 반환 및 캐시 저장 → ⑤ TCP 3-way handshake → ⑥ TLS handshake (HTTPS) → ⑦ HTTP 요청 → ⑧ 응답 렌더링.

- Q: DNS 조회에서 Recursive와 Iterative의 차이는?
  A: Recursive는 Local DNS가 최종 답을 찾을 때까지 모든 조회를 대신 수행해 PC에 결과만 반환. Iterative는 각 DNS 서버가 "다음 서버 주소"만 알려줘서 요청자가 직접 단계별로 물어봄. 실제로 PC↔Local DNS는 Recursive, Local DNS↔Root/TLD/Auth는 Iterative.

- Q: DNS가 UDP를 쓰는 이유는?
  A: 대부분 DNS 패킷이 512byte 이하로 짧아 연결 수립 오버헤드 없이 빠른 응답이 중요하기 때문. 응답이 512byte 초과(DNSSEC, IPv6 등)하거나 Zone Transfer(서버 간 레코드 전체 복제) 시엔 TCP 사용.

- Q: DNS Cache Poisoning이란? 어떻게 방어하나?
  A: 공격자가 위조 DNS 응답을 Local DNS 캐시에 심어 사용자를 악성 서버로 유도하는 공격. DNS가 UDP 기반이라 응답 인증이 없어서 가능. 방어: DNSSEC(응답에 디지털 서명), 소스 포트 랜덤화로 예측 공간 확장, DoH/DoT로 DNS 쿼리 암호화.

- Q: DNS Amplification 공격이란?
  A: 출발지 IP를 피해자로 위조한 DNS 요청을 오픈 리졸버에 대량 전송. 응답이 요청보다 수십~수백 배 커서 피해자에게 DDoS 증폭 효과. 대응: 오픈 리졸버 차단(내부 IP만 허용), Response Rate Limiting.

- Q: DNSSEC과 DoH의 차이는?
  A: DNSSEC은 DNS 응답에 디지털 서명을 추가해 위조/변조를 검증. 암호화는 아니라 패킷 내용은 보임. DoH는 DNS 쿼리 자체를 HTTPS로 전송해 암호화. ISP나 중간자가 DNS 쿼리 내용을 볼 수 없음. 둘은 목적이 다르며 함께 사용 가능.

- Q: CNAME과 A 레코드의 차이는?
  A: A 레코드는 도메인을 IP에 직접 매핑. CNAME은 도메인을 다른 도메인(별칭)에 매핑. CNAME은 추가 DNS 조회가 필요하지만 IP 변경 시 원본 A 레코드만 수정하면 모든 CNAME이 자동 반영. CDN, 로드밸런서 도메인에 자주 사용.

- Q: /etc/hosts와 DNS의 우선순위는?
  A: /etc/hosts가 DNS보다 먼저 조회됨. 로컬 네트워크에서 스위치/장비 이름을 hosts에 등록하면 DNS 서버 없이도 이름으로 접속 가능. 단, 해당 호스트에서만 적용. DNS Hijacking 공격 중 하나가 악성코드로 hosts 파일을 변조하는 것.
