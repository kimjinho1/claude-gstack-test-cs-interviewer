# 01-12 CORS (Cross-Origin Resource Sharing)

## 개념

브라우저의 **Same-Origin Policy(동일 출처 정책)** : 기본적으로 다른 출처의 리소스 요청을 차단.
**CORS**: 서버가 "이 출처는 허용한다"고 명시적으로 허락하는 메커니즘.

**Origin(출처)**: `프로토콜 + 도메인 + 포트` 조합

```
https://nms.company.com:443  ← Origin
  └ 프로토콜: https
  └ 도메인:   nms.company.com
  └ 포트:     443
```

셋 중 하나라도 다르면 다른 출처(Cross-Origin).

---

## 동작 원리

### Same-Origin Policy가 필요한 이유

```
공격 시나리오:
① 사용자가 bank.com에 로그인 (세션 쿠키 저장)
② 악성 사이트 evil.com 방문
③ evil.com의 JS: fetch("https://bank.com/transfer", {method: "POST", ...})
④ 브라우저가 bank.com 쿠키를 자동 포함해서 요청 전송
⑤ bank.com: 정상 세션으로 인식 → 송금 실행 (CSRF와 유사)

Same-Origin Policy: ③에서 차단. evil.com → bank.com 요청 불가.
```

### 단순 요청 (Simple Request)

조건: GET/POST/HEAD + 특정 헤더만 + Content-Type 제한
→ Preflight 없이 바로 요청. 서버가 CORS 헤더 응답에 포함.

```
요청:
GET /api/switches HTTP/1.1
Origin: https://dashboard.company.com

응답:
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://dashboard.company.com
← 이 헤더가 없으면 브라우저가 응답 차단 (서버는 받았지만 JS에서 못 읽음)
```

### Preflight 요청

단순 요청 조건 벗어나면(PUT, DELETE, 커스텀 헤더 등) 브라우저가 **OPTIONS로 먼저 허락 확인**.

```
① Preflight (브라우저 자동)
OPTIONS /api/switches/1 HTTP/1.1
Origin: https://dashboard.company.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: Authorization

② 서버 응답
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://dashboard.company.com
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 86400  ← 이 시간 동안 Preflight 캐시

③ 실제 요청
DELETE /api/switches/1
Authorization: Bearer eyJ...
```

### 주요 CORS 헤더

| 헤더 | 방향 | 역할 |
|------|------|------|
| `Origin` | 요청 | 출처 명시 (브라우저 자동) |
| `Access-Control-Allow-Origin` | 응답 | 허용할 출처 (`*` or 특정 도메인) |
| `Access-Control-Allow-Methods` | 응답 | 허용할 HTTP 메서드 |
| `Access-Control-Allow-Headers` | 응답 | 허용할 요청 헤더 |
| `Access-Control-Allow-Credentials` | 응답 | 쿠키 포함 허용 여부 |
| `Access-Control-Max-Age` | 응답 | Preflight 캐시 시간 (초) |

**`*` (와일드카드) 주의사항**

```
Access-Control-Allow-Origin: *  ← 모든 출처 허용
+ Access-Control-Allow-Credentials: true  ← 조합 불가!

쿠키/인증 정보 포함 요청은 반드시 특정 도메인 명시해야 함
```

---

## 자주 하는 실수

```
1. 서버에서 CORS 헤더 안 넣음
   → 브라우저: "Access-Control-Allow-Origin 없음 → 차단"
   → 에러: "CORS policy: No 'Access-Control-Allow-Origin' header"

2. OPTIONS 요청 처리 안 함
   → Preflight에 405 응답 → 실제 요청 안 나감

3. 개발에서 proxy 써서 몰랐다가 프로덕션 배포 후 CORS 에러
   → 서버에 CORS 설정 필요
```

**CORS는 브라우저 정책. curl/서버 간 통신은 적용 안 됨.**

## 예시 코드 (Python)

```python
from flask import Flask, request, jsonify
from functools import wraps

app = Flask(__name__)

ALLOWED_ORIGINS = [
    "https://dashboard.company.com",
    "https://nms.company.com",
    "http://localhost:3000",  # 개발용
]


def cors_headers(response, origin: str):
    """CORS 헤더 추가"""
    if origin in ALLOWED_ORIGINS:
        response.headers["Access-Control-Allow-Origin"] = origin
        response.headers["Access-Control-Allow-Credentials"] = "true"
    response.headers["Access-Control-Allow-Methods"] = "GET, POST, PUT, PATCH, DELETE, OPTIONS"
    response.headers["Access-Control-Allow-Headers"] = "Authorization, Content-Type"
    response.headers["Access-Control-Max-Age"] = "86400"
    return response


@app.after_request
def add_cors(response):
    origin = request.headers.get("Origin", "")
    return cors_headers(response, origin)


# Preflight 처리
@app.route("/api/v1/<path:path>", methods=["OPTIONS"])
def preflight(path):
    return "", 204


@app.get("/api/v1/switches")
def list_switches():
    return jsonify([{"id": 1, "name": "SW-CORE-01"}])


@app.delete("/api/v1/switches/<int:switch_id>")
def delete_switch(switch_id: int):
    return "", 204


# ── CORS 동작 시뮬레이션 ──────────────────────────────

def simulate_cors_check(origin: str, method: str, path: str):
    """브라우저의 CORS 검사 시뮬레이션"""
    print(f"\n[CORS 검사] Origin={origin}, Method={method}, Path={path}")

    # Same-Origin 체크
    server_origin = "https://api.company.com"
    if origin == server_origin:
        print("  → Same-Origin: 허용")
        return True

    # 단순 요청 여부
    simple_methods = {"GET", "POST", "HEAD"}
    needs_preflight = method not in simple_methods

    if needs_preflight:
        print(f"  → Preflight 필요 (method={method})")
        # OPTIONS 요청 시뮬레이션
        if origin in ALLOWED_ORIGINS:
            print("  → Preflight 통과: 허용된 출처")
            return True
        else:
            print("  → Preflight 실패: 허용되지 않은 출처 → 차단")
            return False
    else:
        if origin in ALLOWED_ORIGINS:
            print("  → 단순 요청 허용")
            return True
        else:
            print("  → 허용되지 않은 출처 → 차단")
            return False


simulate_cors_check("https://dashboard.company.com", "GET", "/api/v1/switches")
simulate_cors_check("https://evil.com", "DELETE", "/api/v1/switches/1")
simulate_cors_check("http://localhost:3000", "DELETE", "/api/v1/switches/1")
```

## 면접 예상 질문

- Q: CORS란 무엇이고 왜 필요한가?
  A: 브라우저의 Same-Origin Policy를 완화하는 메커니즘. 기본적으로 브라우저는 다른 출처의 API 요청을 차단함. 서버가 특정 출처를 허용한다는 CORS 헤더를 응답에 포함하면 브라우저가 허용. CSRF 등 크로스 사이트 공격 방어가 목적.

- Q: Preflight 요청이 발생하는 조건은?
  A: GET/POST/HEAD 외 메서드(PUT, DELETE 등), 커스텀 헤더(Authorization 등), Content-Type이 application/json인 경우. 브라우저가 OPTIONS 메서드로 서버에 먼저 허용 여부를 확인.

- Q: CORS는 서버 간 통신에도 적용되나?
  A: 아니다. CORS는 브라우저 정책. curl, 서버→서버 HTTP 요청에는 적용 안 됨. 브라우저가 보안 목적으로 강제하는 것.

- Q: `Access-Control-Allow-Origin: *`의 문제점은?
  A: 모든 출처를 허용해 보안이 약해짐. 또한 `*`와 `Access-Control-Allow-Credentials: true`를 함께 쓸 수 없음. 쿠키/인증 정보 포함 요청은 반드시 특정 도메인을 명시해야 함.
